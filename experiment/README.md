# 실험: SAST vs 동적 2계정 테스트 탐지력 비교

AI 생성 코드에서 흔한 취약점을 **정적 분석(SAST)** 과 **동적 2계정 테스트** 가
각각 얼마나 잡는지 실측한 기록.

> ⚠️ `vulnapp/` 은 **의도적으로 취약하게 만든 테스트 픽스처**입니다.
> 절대 배포하지 마세요. `127.0.0.1` 에만 바인딩됩니다.
> 코드 안의 키·비밀번호는 전부 가짜 고정값입니다.

## 구성

| 파일 | 역할 |
|---|---|
| `vulnapp/server.js` | 취약점 21개를 의도적으로 심은 Express 앱 + **안전한 대조군 1개** |
| `scanner.js` | 동적 2계정 스캐너. 관측으로 증명된 것만 보고 |
| `sast-rules.yml` | semgrep 규칙 (IDOR 탐지 휴리스틱 포함) |
| `run.sh` | 매 실행마다 새 서버를 띄워 상태 오염 방지 |

## 재현

```bash
cd vulnapp && npm install && cd ..
./run.sh                                    # 동적 스캔
semgrep --config sast-rules.yml vulnapp/server.js   # 정적 스캔
```

## 결과

| 방식 | 탐지 | 오탐 |
|---|---|---|
| 동적 2계정 테스트 | **17/21 (80%)** | **0** |
| SAST (semgrep) | 8/21 (38%) | **1** |
| 둘을 합치면 | **21/21 (100%)** | — |

### 핵심 발견: SAST는 취약한 코드와 안전한 코드를 구분하지 못했다

semgrep 이 IDOR 후보로 **두 곳**을 플래그했다.

- `L59 /api/notes/:id` — 소유권 체크 없음. **진짜 취약**
- `L72 /api/cards/:id` — `if (card.owner_id !== req.user.id) return 403` 있음. **안전**

두 코드는 구문상 거의 같다. 차이는 "있어야 할 비교문이 있는가"뿐이고,
**없는 코드는 패턴 매칭의 대상이 아니다.**

→ SAST의 IDOR 정밀도 **50%** (1 TP / 1 FP)
→ 동적 테스트 정밀도 **100%** — 실제로 B의 토큰으로 A의 데이터를 요청해
   notes 는 200, cards 는 403 이 오는 것을 **관측**했기 때문

### 동적 테스트가 놓친 것

`D1` 하드코딩 키 · `D11` 약한 시크릿 · `A11` MD5 해싱 · `F2`

런타임 밖에서는 관측 불가능하다. **소스 분석이 반드시 병행되어야 한다.**

## 실험 중 발견한 설계상 함정

1. **파괴적 테스트가 뒤따르는 테스트를 망친다.**
   IDOR 삭제 테스트가 실제로 레코드를 지워서, 재실행 시 IDOR 읽기 테스트가
   대상을 잃고 탐지에 실패했다.
   → 제품화 시 쓰기/삭제는 **스캐너가 스스로 만든 리소스에만** 적용하거나
     기본값을 읽기 전용으로 두어야 한다. 아니면 고객 데이터를 지운다.

2. **약한 체크는 오탐 제조기가 된다.**
   페이지네이션 상한 검사를 `status === 200` 으로만 판정했는데,
   상한이 정상 동작하는 API 도 200 을 반환한다.
   → 요청한 개수 대비 실제 반환 개수를 비교해야 한다.

3. **서버 인스턴스 중복.**
   같은 포트에 두 프로세스가 떠서 측정값이 흔들렸다. `run.sh` 가 매번 정리한다.

## 부수적 발견: GitHub Push Protection

최초 커밋에는 Stripe 형식(`sk_live_...`)의 가짜 키가 들어 있었고,
GitHub Push Protection 이 푸시를 차단했다. 값 자체는 지어낸 것이었지만
**형식이 실제 제공자 패턴과 일치하면 내용과 무관하게 차단된다.**

우회 URL 이 제공되지만 사용하지 않고, 픽스처를 제공자 형식이 아닌
일반 문자열로 교체했다. 취약 코드 샘플을 다루는 제품이라면 반드시
마주칠 문제이므로 기록해 둔다.
